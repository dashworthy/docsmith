# feature-doc

You turn a **target** — a bundle, module, directory, or named feature — into an architecture handoff:
a cover, a plain-language overview, real diagrams (a component map, an ER model, a process pipeline),
the wire contract, a component→responsibility grid, the edge cases a maintainer must act on, and how
to test it. You own the **template**; `docsmith:docsmith` owns the **PDF rendering**. You fill the
template, then hand it to that skill to produce the document — you do not build the render machinery
yourself.

- `$SKILL` is this skill's base directory (`${CLAUDE_PLUGIN_ROOT}/skills/feature-doc`); its templates
  live under `$SKILL/references/templates/`.
- `docsmith:docsmith` is the PDF builder that renders the filled PDF template — the same plugin, so
  `${CLAUDE_PLUGIN_ROOT}/skills/docsmith` reaches it.

## 1. Understand the target — read the real code

Before authoring a word, map the feature from the source, not from memory:

- The entry points (controllers, commands, endpoints), the core services, and what they depend on.
- The data model (entities, ownership, invariants) — enough for a real ER diagram.
- The process flow from trigger to result — enough for a real pipeline diagram.
- The wire contract (request/response, config payloads) and the classes that carry each responsibility.
- The edge cases and failure modes the code actually handles, and how the feature is tested.

**Describe what the code does — never invent behavior.** If the target already has a README, treat it
as a source, not gospel; verify against the code. If the human handed you material (a spec, notes),
use it, but still ground every claim in the target.

## 2. Pick the format, then fill this skill's template

Ask the reader which format they need, then start from the matching template:

- **PDF (default)** — `$SKILL/references/templates/pdf/feature-doc.pdf.tsx`, a designed A4 document
  authored as JSX against the `@docsmith/docsmith` component library. Rendered by `docsmith:docsmith`.
- **Markdown** — `$SKILL/references/templates/markdown/feature-doc.md`, plain-GFM that renders
  anywhere (a repo, a wiki) with no build step. **Self-contained: you copy it, fill it, and you are
  done — there is no render and no run directory.**

Both carry the same section list and their own fill-in instructions in a header comment. Fill in real
content:

- Replace **every** `<...>` angle placeholder and `TODO —` line with real content, or delete the line.
- **Drop any OPTIONAL section** the feature doesn't need (e.g. omit the data model when there's no
  meaningful one). A shorter true doc beats a padded one. When you drop a section, also delete its
  row from the ToC array, or the PDF renders a ToC entry pointing at a section that isn't there.
- Diagrams are real: model the actual system (a bad mermaid diagram aborts a PDF render naming it).
- Put author/date metadata on the cover, not a footer, and don't add a "generated by" line.

## 3. Render (PDF only) via docsmith:docsmith

**Markdown is finished at step 2** — the filled `.md` is the deliverable; place it where the doc
belongs and stop.

For **PDF**, copy the filled `feature-doc.pdf.tsx` into the run dir as `pdf.tsx` and hand it to
**`docsmith:docsmith`** — follow that skill's workflow (scaffold the run dir, install, render **light**
by default, then verify by looking at the PDF). Offer the reader a dark copy and render `--theme dark`
only if they want one. It owns the component catalog, the render, and the verification protocol; this
skill does not reimplement any of that.
